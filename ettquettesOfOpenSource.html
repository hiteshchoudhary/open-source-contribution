A guide for contributors

Open Source is a Privilege, not a Playground.

Every pull request carries weight. Real maintainers spend real time reviewing your work. Before you contribute, ask yourself: does this add genuine value?

// 01 — foundation

The Core Principles

Value Over Volume

One meaningful contribution is worth more than a hundred trivial ones. Quality signals seriousness; quantity without quality is just noise.

Respect Maintainer Time

Maintainers are often unpaid volunteers. Every review request is time taken from their work and life. Don't waste it on pointless changes.

Understand Before You Act

Read the codebase. Read the CONTRIBUTING.md. Read open and closed issues. Context is not optional — it's the foundation of a good PR.

Solve Real Problems

Great contributions fix bugs, add necessary features, or improve genuine documentation confusion. Trivial cosmetic edits are not contributions.

Communication is Code

How you describe your PR, write commit messages, and respond to reviews matters as much as the code itself. Write clearly and professionally.

Own Your Work

Don't open a PR and disappear. Respond to review comments. If life gets in the way, communicate. Silence after a review is disrespectful.

"Submitting a pull request is not the end goal. Solving a real problem collaboratively, with humility, is."
— The spirit of open source

// 02 — behaviour

Do's & Don'ts

✦ Do This
🔍
Read the CONTRIBUTING guide first Every repo has one. It tells you exactly what's expected. Skipping it is the fastest way to get your PR closed.
🐛
Open an issue before a PR Discuss the problem first. Confirm the maintainer wants the change. This saves everyone time.
🧪
Test your changes locally Make sure your code works. Run existing tests. Don't submit broken work and expect the review process to fix it.
📝
Write descriptive commit messages "Fix null pointer in user auth flow" beats "fix bug" every single time.
🎯
Keep PRs focused and small One PR, one purpose. Smaller diffs are easier to review, easier to merge, and easier to revert if needed.
🙏
Accept rejection gracefully Not every PR gets merged. Learn from feedback. That growth itself is a contribution to your own career.
✕ Avoid This
🚫
Don't add your name to contributor lists Adding yourself to README contributor sections without real work is shameless self-promotion, not open source.
🚫
Don't fix grammar for the sake of a PR Fixing one comma or rewriting a sentence that was already clear wastes maintainer review time and pollutes the git history.
🚫
Don't submit code you don't understand Pasting AI-generated or copied code you can't explain is dishonest and harmful to the project and to your own learning.
🚫
Don't spam issues asking to be assigned "Can I work on this?" on every open issue without context signals you want credit, not to actually help.
🚫
Don't farm contributions for Hacktoberfest swag Contribution farming for T-shirts and stickers is exactly the kind of pollution that burns out maintainers and harms the community.
🚫
Don't ignore review feedback If a maintainer asks for changes, make them or explain your reasoning. Radio silence after a review is rude and unprofessional.

// 03 — before you submit

The Pre-PR Checklist

⚡ Ask yourself before opening that pull request:

  • Have I read the CONTRIBUTING.md or similar guide in this repo?
  • Is this change solving a real, confirmed problem — not just something I felt like changing?
  • Did I open or reference an issue before writing this PR?
  • Have I tested this locally and confirmed it works correctly?
  • Are my commit messages descriptive and meaningful?
  • Is this PR focused on a single concern, not a bundle of unrelated changes?
  • Have I written a clear PR description explaining what changed and why?
  • Am I prepared to respond to review comments promptly?
  • Would I be comfortable if a senior engineer reviewed this PR right now, as-is?

// 04 — what not to look like

Common Anti-Patterns

Anti-Pattern #1

The Name Dropper

Opens a PR solely to add their name to a "Contributors" section. No code. No fix. No value. Just a vanity entry in the git history.

Anti-Pattern #2

The Grammar Troll

Spends more time fixing commas in README files than understanding the project. Every trivial "typo fix" PR takes a maintainer 10 minutes to review.

Anti-Pattern #3

The Hacktoberfest Farmer

Floods repos every October with low-effort PRs to hit a count for free merchandise. Ruins the spirit of the event and burns out real maintainers.

Anti-Pattern #4

The Copy-Paste Dev

Submits code generated by AI or copied from Stack Overflow without understanding it. Breaks tests, ignores edge cases, then blames the project.

Anti-Pattern #5

The Assign Spammer

Comments "assign me!" on dozens of open issues simultaneously with no prior context. Takes the issue, then disappears without delivering anything.

Anti-Pattern #6

The Ghost Contributor

Opens a PR, gets review comments, and never responds. The PR sits open indefinitely, blocking the maintainer from closing or merging anything related.

// 05 — final word

Open Source is a Community,
Not a Resume Line.

The most respected contributors aren't those with the highest PR count — they're the ones who show up consistently, communicate clearly, solve hard problems, and treat every maintainer interaction with professionalism and gratitude.

Be the contributor you'd want reviewing your own project someday.
